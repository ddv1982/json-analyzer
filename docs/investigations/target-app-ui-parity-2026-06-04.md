# Investigation: Target App UI Parity

## Summary
The mismatch is not primarily CSS polish. The current UI still exposes local information architecture, workflow ownership, and implementation-facing copy that the target app does not: a project-status header, seven result tabs, dashboard-first results, input-owned analyze/status flow, a split Values Explorer/duplicate workflow, and capability-oriented Curl copy. The next plan should supersede the prior minimal UI plan and treat the target app’s UX/functionality as the baseline.

## Symptoms
- Current UI still deviates from the target app’s user experience after the minimal UI pass.
- Some text currently visible in the app should not be in the UI.
- The desired direction is stricter target-app parity, not a loose visual inspiration pass.

## Background / Prior Research
- Target app main page is a compact two-column workflow: header with `JSON Analyzer`, subtitle, `Curl Executor` action, and theme toggle; main grid has JSON input left and analysis dashboard right (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/app/page.tsx:29-62`).
- Target result navigation has three top-level tabs only: `Statistics`, `Values`, `Duplicates` (`target frontend/components/analysis/analysis-results.tsx:54-91`). Current app exposes seven tabs in `frontend/src/components/analysis/AnalysisResultsPanel.tsx:6-14`, so parity is structural, not just visual.
- Target input workflow includes JSON input, validation status, flatten nested arrays option, and `Load Example`, `Format`, `Clear`, `Analyze JSON` actions (`target frontend/components/json-input/json-input.tsx:140-243`). Current repo has equivalent primitives but with different copy/action emphasis.
- Target results state machine uses empty, loading, error, and results states (`target frontend/components/analysis/analysis-dashboard.tsx:85-123`, `analysis-empty-state.tsx:31-45`, `analysis-loading-state.tsx:21-37`). Current app distributes some status text through input/status panels.
- Target Values Explorer keeps user-facing product copy but avoids architecture text. It exposes `Values Explorer`, field selection, field/value filters, sort, export/clear actions, and duplicate/unique result panels (`target frontend/components/analysis/values-explorer.tsx:283-431`, `filter-controls.tsx:41-87`, `results-summary.tsx:48-90`).
- Target copy that is product UI includes action/status language such as `JSON Input`, `Ready for input`, `Valid JSON`, `Invalid JSON`, `Ready to Analyze`, `Analyze JSON`, `Re-analyze`, `Statistics`, `Values`, and `Duplicates`. Visible architecture copy is not part of the target UX except target-specific backend-unavailable errors.

## Investigator Findings

### Phase 2 - Current repo UI trace against target baseline
**Hypothesis result:** Confirmed. The current repo has target-adjacent density/styling, but its visible workflow hierarchy and copy remain materially different from the target app. The previous UI pass was framed as visual inspiration rather than functional/UX parity, so it preserved local product structure: a heavier header/nav model, input-owned command/status panels, a seven-tab results surface, a dashboard-first result flow, a more elaborate Values Explorer workflow, and implementation-facing copy.

#### Finding 1 — App shell/header still exposes local architecture and a heavier navigation model
**Current evidence:** `frontend/src/App.tsx:9-12` stores a local `activeView` instead of route state, and `frontend/src/App.tsx:24-56` conditionally swaps the JSON Analyzer workspace with `CurlExecutorView`. `frontend/src/components/common/AppHeader.tsx:21-58` renders an eyebrow (`Local-first desktop MVP`), dynamic page title, longer lede, two nav buttons, theme control, and a visible scope note: `PDF export is intentionally deferred... guarded Rust service execution... in-memory async jobs only.` `frontend/src/components/common/ThemeToggle.tsx:15-34` adds a fieldset legend plus `Using {resolvedTheme} colors` status text.
**Target evidence:** Target main page keeps the top-level page compact: title/subtitle left and only `Curl Executor` plus theme toggle right (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/app/page.tsx:29-50`). Target curl page is a distinct route with a reciprocal `JSON Analyzer` action (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/app/tools/curl-executor/page.tsx:12-23`, `/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/curl-executor/header.tsx:10-23`).
**Conclusion:** The current header is not just visually different; it presents project/status/architecture concepts as primary UI. A new plan must treat the header as a workflow hierarchy change: compact product title/subtitle, one contextual tool switch action, less theme-toggle chrome, and no visible implementation/deferred-scope note in the main header.

#### Finding 2 — JSON input/results state flow is split differently from the target app
**Current evidence:** `frontend/src/state/useJsonAnalyzerState.ts:18-31` initializes with sample JSON and starts on `activeTab: 'dashboard'`; `frontend/src/state/useJsonAnalyzerState.ts:152-180` validates before analysis, clears analysis during the busy state, and then resets the active tab to dashboard. `frontend/src/components/json-input/JsonInputPanel.tsx:47-57` labels the panel as `Input` / `JSON input` and uses `Ready` rather than target `Ready for input`; `JsonInputPanel.tsx:77-80` adds explanatory flatten-copy; `JsonInputPanel.tsx:86-96` exposes both `Validate JSON` and `Analyze JSON` in the input action row. `frontend/src/components/common/StatusPanels.tsx:4-9` and `StatusPanels.tsx:38-42` show implementation copy (`golden-fixture-backed command mocks`, `Tauri command wrapper`) in normal status panels.
**Target evidence:** Target JSON input title/status/action pattern is `JSON Input`, `Ready for input` / `Valid JSON` / `Invalid JSON`, and `Load Example` / `Format` / `Clear` actions in the input card (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/json-input/json-input.tsx:140-177`, `json-input.tsx:219-243`). Target analysis owns the primary `Analyze JSON` action and empty/loading/error/results state machine (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/analysis/analysis-dashboard.tsx:85-123`, `/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/analysis/analysis-empty-state.tsx:31-45`, `/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/analysis/analysis-loading-state.tsx:10-40`).
**Conclusion:** The current app has the primitives but not the same state ownership. A new plan must move visible hierarchy toward target: input is for editing/validation/formatting, while the results panel owns empty/loading/error/results and the primary analyze/re-analyze/clear-results flow. Implementation-only status copy should be removed from product UI or confined to diagnostics/dev-only surfaces.

#### Finding 3 — Results navigation is structurally wrong for target parity
**Current evidence:** `frontend/src/components/analysis/AnalysisResultsPanel.tsx:7-15` declares seven top-level tabs: `Dashboard`, `Structure`, `Statistics`, `Fields`, `Values Explorer`, `Exact duplicates`, and `Min/max filled`. `frontend/src/components/analysis/AnalysisResultsPanel.tsx:71-129` only renders tabs after `analysis` exists; empty state falls through to `EmptyState`. `frontend/src/components/analysis/ResultView.tsx:18-35` maps every top-level tab to a separate view, and `frontend/src/components/analysis/views/Dashboard.tsx:6-31` introduces a dashboard summary plus embedded duplicate/min-max panels before target tabs.
**Target evidence:** Target results card has title/actions and exactly three top-level tabs: `Statistics`, `Values`, and `Duplicates` (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/analysis/analysis-results.tsx:31-92`). Target starts/restarts results on `statistics`, not a dashboard (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/analysis/analysis-dashboard.tsx:30-34`, `analysis-dashboard.tsx:72-83`).
**Conclusion:** This is the clearest proof that the previous pass was cosmetic. A parity plan must collapse/re-home Dashboard, Structure, Fields, and Min/max so the visible top-level result model is the target three-tab model. Keeping seven tabs but restyling them cannot satisfy the target baseline.

#### Finding 4 — Values Explorer contains target primitives but the workflow shape diverges
**Current evidence:** `frontend/src/components/analysis/values-explorer/ValuesExplorerView.tsx:331-366` starts with a selected-field summaries subpanel, `ValuesExplorerView.tsx:370-481` automatically runs grouped-values analysis with value search/sort/page-size/source controls, and `ValuesExplorerView.tsx:483-574` adds a separate `Duplicate analysis` launcher. It includes implementation/workflow copy such as `Discover fields, select up to...`, `Grouped values update locally; use the duplicate workflow below...`, `advanced field duplicates`, `composite duplicate keys`, and duplicate page-size cap explanations (`ValuesExplorerView.tsx:324-327`, `ValuesExplorerView.tsx:419-421`, `ValuesExplorerView.tsx:488-497`, `ValuesExplorerView.tsx:534-545`).
**Target evidence:** Target Values Explorer is a collapsible card headed `Values Explorer`, then field selection, filter controls, sort, results summary/panels, and bottom actions `Export PDF` / `Clear Results` (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/analysis/values-explorer.tsx:283-430`). Target filter controls are a compact field/value/clear row (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/analysis/values-explorer/filter-controls.tsx:40-89`) and target results summary emphasizes `Total Records`, `Unique results`, `Duplicate results`, and `Field Set` (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/components/analysis/values-explorer/results-summary.tsx:48-90`).
**Conclusion:** The current Values Explorer over-exposes backend analysis modes and splits grouped values from duplicate analysis in a way the target does not. A new plan must define the desired target-like Values workflow first, then map current capabilities into that shape; copy-density tweaks alone will leave the workflow feeling unlike the target.

#### Finding 5 — Curl Executor is implemented as an in-app view and uses capability/config copy rather than target task guidance
**Current evidence:** `frontend/src/components/curl-executor/CurlExecutorView.tsx:277-314` labels the panel `Parse, preview, execute, and batch curl commands` and shows a status badge like `Jobs + batch enabled`. `CurlExecutorView.tsx:317-340` explains guarded Rust service execution, redacted previews, in-memory jobs, disabled configuration, and batch internals. The controls then offer `Parse / Preview`, `Execute once`, `Start async job`, `Start batch job`, `Cancel job`, and config-disabled warnings (`CurlExecutorView.tsx:395-439`, `CurlExecutorView.tsx:442-454`).
**Target evidence:** Target curl route composes `Header`, `Instructions`, `CurlCommandSection`, progress/error/results sections (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/app/tools/curl-executor/page.tsx:12-23`). Target header says `Execute curl commands directly from Postman - simple, secure, and universal` (`components/curl-executor/header.tsx:10-23`), target instructions are task steps (`instructions.tsx:9-77`), and target command section centers on `Curl Command`, `Execute`, `Batch Mode`, resource IDs, concurrency, and timeout (`curl-command-section.tsx:37-172`).
**Conclusion:** The current curl surface is feature/capability-oriented, while the target is task-oriented. A new plan must either explicitly accept this product difference or reframe Curl Executor as a target-like route/workflow; simply sharing global styles with the JSON analyzer will not close the UX gap.

#### Finding 6 — Global styles still encode a bespoke dashboard hierarchy, not target-like content hierarchy
**Current evidence:** `frontend/src/styles.css:205-238` creates a bounded app shell plus two-column header with aside; `styles.css:247-258` defines all-caps eyebrow/kicker hierarchy; `styles.css:260-271` styles the visible scope note; `styles.css:281-337` makes app nav and theme toggle segmented controls with extra status text. `styles.css:347-351` fixes the main JSON workspace to two equal columns, `styles.css:356-364` gives all panels/cards/states shared card treatment, `styles.css:418-430` forces generic textareas to `min-height: 56vh`, and `styles.css:548-576` styles tabs as a generic horizontal overflow tab list. Values-specific layout reinforces the current expanded workflow with selected-field and duplicate-launch grids (`styles.css:988-1010`, `styles.css:1051-1077`, `styles.css:1111-1124`).
**Target evidence:** Target baseline is a compact container, separator, and two-column content grid (`/Users/vriesd/projects/qa-toolbox/json-analyzer/frontend/app/page.tsx:26-63`), with card/tab/control primitives used to support the product workflow rather than introduce extra hierarchy.
**Conclusion:** The global CSS pass reduced/changed chrome but preserved current hierarchy hooks. A new plan must start from target information architecture and then restyle primitives to support that hierarchy; otherwise the same styles will continue to elevate local-only constructs such as eyebrows, scope notes, seven tabs, and duplicated nested cards.

#### Finding 7 — Prior plan language explains why the pass missed parity
**Evidence:** `docs/plans/minimal-target-like-ui-2026-06-03.md:3-6` scopes the work to making the app `feel closer` through calmer hierarchy/density while preserving current architecture. `docs/plans/minimal-target-like-ui-2026-06-03.md:51-55` explicitly says target references are `design inspiration for proportion and density`, not parity instructions.
**Conclusion:** Root cause is planning scope, not just execution quality. The next plan should name the target app as the UX/functionality baseline, list non-negotiable visible IA/copy deltas, and decide intentionally where current Rust/Tauri-only capabilities should be hidden, reworded, or surfaced as target-compatible product affordances.

## Investigation Log

### Phase 1 - Initial assessment
**Hypothesis:** The previous plan under-specified target-app parity and allowed local deviations, especially around explanatory copy, custom control treatment, and feature workflow shape.
**Findings:** The existing plan explicitly treats the target app as design inspiration rather than implementation parity, which conflicts with the updated user requirement.
**Evidence:** `docs/plans/minimal-target-like-ui-2026-06-03.md` states: “Target-app references are design inspiration for proportion and density, not instructions to copy Tailwind/Radix implementation details.”
**Conclusion:** Confirmed. New plan should use target app as the UX/functionality baseline and identify exact deltas.

## Root Cause
The previous UI work optimized the current app’s existing hierarchy instead of replacing that hierarchy with the target app’s workflow model. The prior plan explicitly framed the target app as visual inspiration, so implementation preserved local-only concepts: `AppHeader` exposes MVP/deferred/Rust job copy, `AnalysisResultsPanel` keeps seven top-level tabs, `useJsonAnalyzerState` starts on `dashboard`, the input panel owns both validate/analyze actions, Values Explorer exposes grouped values and duplicate launch as separate workflow regions, and Curl Executor leads with guarded service/job capability language.

This rules out a CSS-only fix. CSS can support the final result, but the real fix is target information architecture first, copy cleanup second, styling last.

### Eliminated Hypotheses
- **Only density/styling is wrong:** eliminated. Seven top-level tabs, dashboard-first state, and split Values/Duplicates workflows are structural mismatches.
- **The header only needs lighter styling:** eliminated. Visible copy like `Local-first desktop MVP`, deferred PDF scope, guarded Rust service execution, and in-memory jobs should be removed from product UI, not muted.
- **Accessible primitives are blocking parity:** eliminated. Existing tab, dropdown, combobox, theme, and command-wrapper contracts can be preserved while changing hierarchy and copy.
- **Tauri/Rust architecture prevents parity:** eliminated. Runtime architecture can remain; implementation details should move to docs/dev diagnostics instead of main UI.
- **Parity requires Tailwind/shadcn/Radix migration:** eliminated. The target’s UX patterns can be mapped into this repo’s React/global-CSS component system.

## Recommendations
1. **Supersede `docs/plans/minimal-target-like-ui-2026-06-03.md` with a stricter target-parity plan.** The plan should state that target UX/functionality is the baseline, not inspiration. Current UI structure may be removed or re-homed even if tests currently assert it.
2. **Lock target-compatible result information architecture before styling.** Top-level result tabs should become `Statistics`, `Values`, and `Duplicates`. Re-home Dashboard, Structure, Fields, Min/max, and Exact duplicates into those tabs or remove their top-level visibility. Start result navigation on `statistics`, not `dashboard`.
3. **Move analysis state ownership toward the results panel.** JSON input should focus on edit/load/format/clear/validation/flatten. Results should own empty/loading/error/results, `Analyze JSON`, and re-analyze/clear-results flow, matching the target state machine.
4. **Rewrite the header as a product toolbar.** Keep title, short target-verified subtitle if needed, contextual JSON Analyzer/Curl action, and theme toggle. Remove visible MVP, architecture, deferred-scope, Rust-service, and in-memory-job text.
5. **Rework Values Explorer as one target-like workflow.** Field selection, filters/sort, summary, grouped values, and duplicate/unique results should feel like one flow. Keep functional labels, counts, field paths, warnings, errors, and pagination; remove backend-mode and explanatory workflow copy.
6. **Reframe Curl Executor as task-oriented.** Lead with command input, execute/batch controls, progress, parsed request, response, errors, redaction, and blocked/allowed states. Do not lead with capability/config/job architecture copy.
7. **Run CSS polish after structural parity.** Tune shell spacing, cards, tabs, controls, popovers, tables, and responsive behavior only after the target hierarchy and copy model are in place.
8. **Update tests to assert the new baseline.** Keep accessibility/theme/Tauri-wrapper behavior tests, but update text/tab/header tests that currently encode the wrong UI.

## Preventive Measures
- Add a UI parity checklist to the next plan: does this match target workflow, is this text visible in target, is this implementation copy, is this top-level navigation target-compatible, and is this functional/accessibility-critical copy?
- Classify every visible string before editing: remove, de-emphasize, accessible-only, keep as functional/status/error/accessibility-critical, or target-source verification required.
- Keep architecture/deferred-scope details in README/CONTRIBUTING/ADRs/dev diagnostics, not main product UI.
- Require target source or screenshot verification for ambiguous details: exact header subtitle, result tab labels, Values Explorer summary layout, and Curl task sequence.
- Sequence future implementation as: information architecture → workflow ownership → visible copy removal → accessibility-preserving markup updates → CSS density/polish → validation and visual smoke.
